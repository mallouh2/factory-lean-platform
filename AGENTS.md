Its purpose is to find where production time, output, and money are lost, determine why, and help management reduce those losses. Follow the loop: **Plan → Execute → Capture loss → Find cause → Action → Verify → Measure value → Next problem**.
- After implementing a material product capability, review `docs/PRODUCT_DIFFERENTIATORS.md`. Update it only when the change materially affects competitive differentiation, parity, or a documented competitive opportunity. ## Production and machine invariants

- `evaluateFlow` is the single source of truth for effective production flow. Physical machine state differs from production flow state. An **OPEN `production_transfer`** is assignment truth: a borrowed alternative stays borrowed, even if it stops, until the transfer is explicitly ended. Temporary borrowing never changes the machine's permanent `line_id`.
- Group 2 supersedes the earlier execution-only physical-state rule: Start synchronizes participating assigned machines to Running; Finish returns machines without other active work to Idle. Preserve legitimate Stopped/Setup/Offline states and open downtime, and never change transfer lifecycle automatically. An open transfer remains assignment truth even if its alternative stops or its order finishes. Reject Running without active work; derive line production state from active execution and the existing effective-flow engine. Pause/Resume requires active line work; Resume restores only eligible pause-idled machines. Validate stop impact against configured roles and explicit process requirements in the backend, not an operator override. Keep downtime reasons, immutable context, permissions and status audit.
- Every work center has `category_id`, its compatibility family. A shared category does not automatically configure alternatives; alternatives are explicit. Cross-category alternatives and transfers are invalid. Saving alternatives must never modify, delete, or reconstruct `work_center_capabilities`.
- Pause is intentional, not a stoppage. Resume restores only machines automatically idled by that pause and still eligible; it must not overwrite later manual states. The repository's flow and transfer rules govern borrowed machines returning to paused lines.

## Requests, Planning V2, and Execution V2

- One Production Request contains multiple Product Items; each item can be planned and executed independently. Required By is the customer/business deadline. Do not aggregate unlike quantities such as meters and pieces.
- Planning V2 is frozen. Planning assigns line and planned start/finish, never operator or technician. Rate, setup, and working calendar determine duration. Existing jobs never move automatically; there is no cascading reschedule. Smart Slot is advisory. Locked schedule changes follow replanning history and reason rules. Generic writes cannot bypass Planning validation.
- Execution Phase 1 separates **PLANNED = planning truth** from **ACTUAL = execution truth**. Execution never overwrites planned timestamps. Start and Finish record actual timestamps using database/server time. At most one Product Item may be active per line. The queue derives from persisted Planning schedule; execution does not reschedule later jobs. Planning lock does not block normal execution.
- F34/F34.1 provide reasoned actual order interruption and selected scheduled-order dispatch, distinct from line Pause and Finish. Floor Start/Pause/Switch/Resume/Finish must preserve the approved line, planned timestamps and all Planning revisions. Pause & Release frees actual capacity and unused shift reservations; a paused order remains scheduled and must not automatically reacquire bookings. Resume the same item without mandatory replanning, using current remaining work and protected current-shift/material/capability/permission checks. Unschedule/Reschedule belongs only to explicit Planning actions. Preserve first actual start, cumulative output/Scrap/Quality/consumption and immutable run/command actors, reasons and planned/effective windows; current-run identity rejects stale recording/Finish while committed retries recover once. Browsing the selector is not execution; audit the confirmed selected-order Start/Resume. Never silently move jobs, end transfers, clear legitimate stops, reconcile legacy custody or create replacements. F34.1 supersedes F34's earlier clearing of the assignment on interruption; retain historical evidence. F37 dual-Gantt plan/revision/actual comparison is future Lean work, not implemented. See `docs/production-order-interruption.md`.
- Post-F34.1 reason/outcome rules: first assignment and reassignment of a currently wholly unscheduled order need no reason, regardless of historical scheduling. Start/Resume needs no reason solely for early/late execution; a priority override requires an earlier currently executable order, identified in the confirmation and audit. Exclude blocked/ineligible earlier orders using current custody, material, machine, Quality and capability checks. Explicit reschedule/unschedule, priority override and Pause & Release retain their reason/impact safeguards. Recheck priority under the original locks; record actual deviations automatically and distinguish a routine blank reason from an actor explanation. The Floor selector is a read-only line timeline; completed/cancelled/zero-or-unknown-remaining work is not executable. Preserve true interval widths and stable production lanes independently of annotation size or viewport. Distinguish a transactionally proven rejection, a committed operation with unavailable refresh, and an unknown transport outcome. Reconcile the actor/item/request receipt; retain an unresolved exact intent/UUID across reloads and never invent a replacement retry identity or claim an absent receipt proves failure. These are locally verified changes, not owner acceptance of F34.1.
- A definitive execution rejection must also retain its actor/item/intent-bound UUID in the existing request audit. Admission locks must survive the failing command subtransaction. Neither a delayed wrapped retry nor a direct execution command may later execute that rejected UUID after conditions change; a fresh reviewed request uses a new identity. This rejection receipt records an attempt only, never production, consumption or a Planning revision. Do not backfill historical failed attempts.
- Warehouse Min/Max detection uses authoritative projected inventory at or below Minimum. Creating STOCK_REPLENISHMENT requires explicit confirmation by a person with Warehouse edit permission; automatic Sales shortage production remains separate. Warehouse never schedules production.
- Use the shared human readable duration formatter for durations, not timestamps: `45 min`, `1 h`, `1 h 30 min`, `5 h`, `1 d 1 h`. Preserve signed variance and EN/AR behavior; do not display long durations only as total minutes.

## Product, material and supply ownership

- Products defines manufactured finished Products and intentionally reusable manufactured intermediates. A compound is a manufactured Product with a kg stock unit; its versioned recipe uses explicit kg ingredients per 1 kg output. Finished Product weight per configured stock unit is explicit. Requirements are theoretical; recipes never automatically issue inventory.
- Warehouse defines only non-manufactured RAW_MATERIAL, ACCESSORY and PACKAGING identities. Preserve legacy SEMI_FINISHED materials until their semantics are reviewed; never blindly convert them. Production WIP stays on durable unfinished lots, with separate stored/floor locations and remaining work. A location receipt/issue never changes the total physical lot quantity; processing does.
- Warehouse presents one primary row per Product, with typed historical-unit details. Finished, stored WIP, active remaining and future incoming are separate. Unknown primary-unit quantities remain unknown; never aggregate unlike units. Scrap is never stock.
- Legacy Good recording credits finished inventory immediately; its Warehouse acknowledgment never adds inventory again. After a factory's first Manufactured Output activation, new eligible recording must enroll in the protected manufactured path: Quality release alone is not inventory, and physical Warehouse receipt credits it exactly once. Hard pause preserves history and authorized committed-result replay, blocks fresh manufactured writes, and never restores legacy admission. Activation remains an explicit privileged factory-specific operation; unsupported unclassified carryover WIP blocks the initial pilot. See `docs/manufactured-output-activation.md`. Stock purchases use the existing External Receipt ledger exactly once. Free-text direct purchases are received by their original requester and create no stock movement.
- Material requests and Purchasing use authenticated server actors/times, per-person grants, protected database transitions and retry IDs. Min/Max requests always require human confirmation; BOTH requires a deliberate sourcing decision. Ordered/ready purchases contribute Incoming; merely requested purchases suppress duplicates without inventing Incoming. No auto-approval, full MRP or unapproved accounting automation. Group 1C explicitly authorizes automatic theoretical raw consumption only for the activated shared Production Stock workflow; preserve all other material contracts.

- Group 1C uses independent multi-material Warehouse requests and shared Production Stock. Reserve current-shift expected output from existing rate/calendar/shift/BOM contracts, never an entire multi-day target. Actual theoretical consumption uses Good plus new WIP weight plus actual Scrap kg; the BOM allowance is forecast-only and startup Scrap is counted once. Freeze actual factors for approved corrections. Deliveries/returns transfer custody once; reservations and handover counts never consume or silently adjust stock. Serialize accounting and retry identities; preserve per-person permissions and existing manufactured-source/WIP contracts. Do not invent historical custody or backfill inventory at cutover. Handover discrepancy evidence and unresolved follow-up notes remain durable. See docs/production-stock-shift-handover.md.
